# Lead Check

Lead Check — веб-приложение для проверки и оценки лидов Worrki. Оно принимает JSON заявки, ищет публичные сведения о человеке и компании, сопоставляет найденное с заявкой и показывает оценку с объяснением и ссылками на источники. Внизу формируется JSON с результатом для CRM.

## Как работает проверка

1. Пользователь вставляет JSON или загружает пример. Интерфейс проверяет синтаксис и обязательные поля, показывает ошибку и позволяет отформатировать ввод.
2. При нажатии «Проверить лид» приложение ищет отчёт для этого JSON в IndexedDB браузера. Найденный отчёт показывается вместе с датой проверки без нового запроса к OpenAI. Кнопка «Выполнить проверку заново» запускает свежий поиск.
3. Сервер делает два поисковых запроса через OpenAI Responses API с `web_search`: отдельно по компании и её деятельности, отдельно по человеку и его роли. Модель возвращает адреса страниц и дословные цитаты по конкретным сведениям заявки.
4. Сервер открывает страницы, для которых предложены цитаты, и проверяет их наличие в доступном HTML, тексте или PDF и совпадение имени человека или названия компании. Для сведений о местоположении и противоречий по деятельности запись на стороннем сайте дополнительно связывается с источником, подтверждающим профиль бизнеса: совпадением сайта, телефона или страницами на одном сайте компании. Общий домен каталога или соцсети такой связью не считается. Если общей связи нет, запись остаётся видимой, но не меняет баллы и не считается доказанным противоречием; различия сайтов и направлений бизнеса отмечаются в отчёте. Страница с ошибкой, непроверенная цитата или похожее название не становятся доказательством.
5. На основании принятых доказательств приложение рассчитывает `Lead score`, `Verification confidence` и категорию HOT, WARM или COLD. Отчёт содержит расшифровку баллов, статусы проверенных сведений, риски, итог для менеджера и ссылки на источники.
6. Успешный отчёт сохраняется в IndexedDB. При новой проверке прежние цитаты перепроверяются, даже если новая поисковая выдача не показала старую страницу. Интерфейс показывает изменение баллов, статусов и источников по сравнению с сохранённым отчётом. Если повторная проверка потеряла ранее принятое подтверждение без прямого противоречия, прежний отчёт остаётся видимым как исторический, а его оценка не выдаётся за свежую; JSON для CRM в этом состоянии скрыт. Отчёты старой версии алгоритма пересчитываются без повторного использования прежних цитат как доказательств.

Поиск может находить и другие ссылки. Они перечислены в отчёте для ручного просмотра, но не считаются проверенными, пока модель не указала цитату, а сервер не подтвердил её на странице. Состав выдачи и доступность сайтов могут меняться. Отсутствие публичного подтверждения не означает, что сведения заявки ложны.

## Оценка

`Lead score` — оценка бизнес-потенциала по найденным признакам, от 0 до 100. Учитываются компания и местонахождение (до 20 баллов), профиль бизнеса (до 30), доступ к кандидатам (до 20), полномочия представителя (до 20) и международное направление (до 10). Баллы за неподтверждённые слова из заявки не начисляются. Сведение на доступной, но неофициальной странице получает половину веса. HOT требует высокого балла и официальных подтверждений ключевых сведений; WARM начинается с 35 баллов при отсутствии ключевого конфликта; остальные заявки получают COLD. Низкий балл при нехватке доказательств означает низкий приоритет по найденной информации, а не доказанную недостоверность лида.

`Verification confidence` — отдельная оценка покрытия проверки, а не вероятность правдивости заявки. Она суммирует подтверждения компании (25), деятельности (25), связи человека с компанией (20), его роли (20), города или адреса (10). Официальный источник даёт полный вес критерия, другое публичное заявление — половину, частичное совпадение — четверть. В отчёте показано начисление по каждому критерию.

Для каждого сведения указаны статус, использованная цитата и ссылка. Статусы различают официальное подтверждение, заявление на публичной странице, частичное совпадение, историческое упоминание, неоднозначную принадлежность источника, противоречие и отсутствие публичного подтверждения. Итог для менеджера и флаг `review_required` помогают понять, что стоит уточнить вручную.

## Данные и ограничения

Обязательные поля JSON: `lead_id` — положительное целое число, `name` и `company_name` — непустые строки. Остальные поля необязательны; дополнительные поля заявки сохраняются. Ввод проверяется схемой Zod. Ключ OpenAI используется только на сервере.

IndexedDB хранит отчёты только в текущем браузере. Ключ кэша зависит от содержимого заявки, поэтому изменение данных запускает новую проверку. Результаты старой версии алгоритма автоматически перепроверяются. Временная недоступность источника не стирает прежний отчёт, но его актуальность требует ручной оценки.

Наличие цитаты на странице подтверждает, что страница содержит эти слова; оно само по себе не доказывает независимость источника или истинность заявления. Приложение показывает происхождение и ограничения доказательства. Реальная отправка в CRM не настроена: раздел `CRM OUTPUT` готовит JSON, который можно скопировать и использовать для интеграции.

## Запуск

Требуются Node.js, npm и ключ OpenAI API. Создайте `.env.local` в корне проекта:

```env
OPENAI_API_KEY=your_api_key
```

Файл `.env.local` исключён из Git.

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Приложение также можно развернуть на Vercel, указав `OPENAI_API_KEY` в переменных окружения проекта.

## API

`POST /api/analyze` принимает JSON лида. При повторной проверке интерфейс передаёт объект с `lead`, `previous_sources` и `previous_evidence`. Прежние цитаты проверяются на страницах снова и не принимаются только потому, что они были в старом отчёте.

После валидации маршрут возвращает поток NDJSON: события `progress` отражают реальные стадии обработки, затем приходит `verified` с отчётом либо `error` с безопасным сообщением. Искусственных задержек нет. До начала потока неверный JSON получает HTTP 400, неподходящие данные — 422, слишком большой запрос — 413. После начала потока ошибка передаётся событием без изменения HTTP-статуса. Редактирование ввода отменяет текущий запрос и очищает показанный результат.
